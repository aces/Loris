# Candidates

## Purpose

The candidates module is where users find, register, review and edit
candidates. It has four pages:

- The candidate list, at `/candidates/`, referred to as "Access Profile" in
  the LORIS menus. Users access specific candidates from it while browsing
  LORIS data.
- The New Profile page, at `/candidates/new-profile/`, which creates a new
  candidate.
- The candidate profile, at `/candidates/$CandID`, a dashboard in which a
  user sees an overview of all data related to a specific candidate across
  all installed and active modules.
- The candidate parameters, at `/candidates/parameters/?candID=$CandID`,
  where users enter candidate data that is not timepoint specific.

## Intended Users

The candidate list is primarily used by data entry staff to reach a
candidate's timepoint list (the `timepoint_list` module, which further
navigates to `instrument_list`) and perform data entry. Other user groups
use it to filter candidates and review their data status.

The New Profile form is used by data entry staff to create candidates for
data entry, and by users uploading imaging data to ensure that a candidate
exists before uploading the image.

The candidate profile is for any user interacting with candidate data.

The candidate parameters are used by data entry personnel, and by site
coordinators who are validating the data.

## Scope

The module lists candidates and links to other relevant LORIS modules
where applicable. It creates candidates, but not their timepoints,
batteries, or anything else related to them.

The candidate profile is only concerned with candidate level data. It is
not used for data entry, only for a candidate overview. Modules which
provide widgets link to the appropriate pages in their module for data
entry.

The candidate parameters store all information for a candidate that is not
timepoint dependent. All data collected during a visit is entered as an
instrument at the visit level.

## Permissions

Any of `data_entry`, `access_all_profiles`, `candidate_parameter_view` or
`candidate_parameter_edit` opens the module. Each page then checks its own:

- The candidate list requires either the `data_entry` permission
  (_"Access Profile: View/Create Candidates and Timepoints - Own Sites"_) and
  at least one study site, or the `access_all_profiles` permission
  (_"Access Profile: View Candidates and Timepoints - All Sites"_). Users with
  `access_all_profiles` see every candidate in LORIS, while users with only
  `data_entry` see the candidates at the study sites they are affiliated
  with.
- The New Profile page requires the `data_entry` permission and at least
  one site.
- The candidate profile requires access to the candidate, by its
  registration project and site or one of its timepoints. Modules which
  register widgets check their own permissions.
- The candidate parameters require `candidate_parameter_view` (view every
  tab) or `candidate_parameter_edit` (edit every tab), and the candidate's
  site. The Participant Status, Caveat and Candidate Parameters terms and the
  Consent Summary card on the candidate profile require the same
  permissions.

## Configurations

- `useEDC`: shows the "EDC" column in the candidate list, and prompts for
  the EDC of the candidate being created.
- `useRegistrationCohort`: requires a registration cohort from the selected
  project when creating a candidate.
- `StartYear`, `EndYear`, `AgeMin`, `AgeMax`: determine whether a new
  candidate's date of birth is within the range of the study protocol.
- `PSCID`: determines whether the PSCID for a new candidate is
  autogenerated or prompted for, and the format of a valid PSCID.
- `useProband`: shows the _Proband_ tab of the candidate parameters.
- `useFamilyID`: shows the _Family_ tab of the candidate parameters.
- `useConsent`: shows the _Consent Status_ tab of the candidate parameters.

The _Candidate Information_ tab of the candidate parameters displays
customized fields configured in the database. The following SQL tables
affect the behaviour of these fields:

- `parameter_type_category`: identifies the categories for
  `parameter_type` entries. This table requires an entry for the
  _Candidate Parameters_ category for customizations to take effect.
- `parameter_type`: lists fields, and all of their attributes, that are
  displayed on the _Candidate Information_ tab.
- `parameter_type_category_rel`: associates the Candidate Parameters from
  the `parameter_type` table with the entry in `parameter_type_category`.
- `parameter_candidate`: stores the values saved for each custom field.

## Interactions with LORIS

The "Scan Done" column of the candidate list indicates whether a scan was
performed for that candidate. If one was, the column links to the
`imaging_browser` module prefiltered for that candidate.

The PSCID column links to the `timepoint_list` page for that candidate.
Users who do *not* have the `access_all_profiles` permission only see, and
navigate to the `timepoint_list` page of, candidates from the sites they
are affiliated with. For these users, the _Open Profile_ button opens a
form that takes a candidate's CandID and PSCID, so that they can access a
candidate whose identifiers they already know.

Upon candidate creation, the New Profile page links to the
`timepoint_list` page of the new candidate.

The candidate profile retrieves basic candidate and visit level data from
the LORIS API to pass to widgets. It calls `getWidgets` on each module with
the widget type `candidate`. The options include a `candidate` key, the
`\Candidate` object for the candidate whose dashboard is displayed, and it
expects an array of `\LORIS\candidates\CandidateWidget` as a result. The
Candidate Info card calls `getWidgets` with the type `candidateinfo` and
expects an array of `\LORIS\candidates\CandidateInfo` terms.

The module's query engine provides the candidate fields of the `dataquery`
module.

The candidate information is exported to the old Data Query Tool (DQT) by
the `CouchDB_Import_Demographics.php` tool script, which needs the same
changes as any field added to the candidate parameters.
